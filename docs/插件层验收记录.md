## 三、发现并修掉的真问题（cwd 漂移）

**现象**：首轮 `vt_probe` 报告的产物根是 `D:\lk\tools\output`，而非项目目录。

**判因**：插件用 `spawnSync` 调 `vt_pipeline.py` 时**未传 `cwd`**，子进程继承宿主进程的工作目录；
而 `vt_pipeline` 的默认产物根是**相对路径** `output` ⇒ 产物落点随宿主 cwd 漂移。

**实测取证**：同一 `probe` 在不同 cwd 下报告不同产物根（宿主安装目录 vs 项目目录）。

**修法**：插件显式传 `cwd: skillRoot`。修复后复测产物根固定为 `<skillRoot>\output`，且误落点无残留。

> 这条正是"**接口成功 ≠ 结果达成**"的又一实例：`vt_probe` 返回 `ok:true` 时，
> 产物其实正落在没人预期的目录里。

## 四、为什么手写 ESM 而不走 tsc

`scripts/build.sh`（脚手架生成）需要 `DSH_CHECKOUT` 指向**带 `packages/` 的源码 checkout**，
并从中链接 `vendor/cordis`、`packages/core/tools` 等。**本机实测只有 npm 安装版**
（`~\.dsh-win\prefix\node_modules\@deepseek-ai\dsh`），无 `packages/`、无 `tsc`
⇒ 构建脚本无法运行（`dev_self_test` 亦报 `无 DSH_CHECKOUT`）。

生态既有先例：已注入的 `@dsh-external/dsh-frozen-injection` **同样手写 ESM**，其源码注释写明同因——
"构建脚本需 DSH 源码 checkout（本机只有 npm 全局包），而编译产物的唯一目的是让宿主能 import"。

本插件无类型擦除需求（只用 `node:` 内置模块 + 宿主 `ctx` 能力），故直接产出等价 ESM，
`node --check` 通过且**已实测可加载运行**。`src/index.ts` 保留为等价 TS 源，待有源码 checkout 时可改用编译链。
