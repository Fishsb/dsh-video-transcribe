## 一、致命项：主路线在 WSL 下不可用

### 实测

```
$ python3 skill/scripts/vt_pipeline.py probe
  ffmpeg   : （缺失：可用 VT_FFMPEG 指定全路径）
  ffprobe  : （缺失：时长回退解析 ffmpeg -i，仍可工作）
  宿主 ASR  : {"ok": true, "modelReady": true, "model": "sense-voice"}
  主路线可用性: 不可用（见上）
$ echo $?   # （不经管道）→ 2
```

- `/usr/bin/ffmpeg`、`/usr/local/bin/ffmpeg`、`/snap/bin/ffmpeg` **三处均无**（全盘 find 亦无）
- `probe` 用了**正确**的退出码语义（不可用 = 2），**这一点做得好**，不是缺陷

### 成因（不是代码 bug）

`docs/本机环境事实.md` 记的是 **Windows 侧**事实：`ffmpeg` ✅ 在 PATH。
迁 WSL 后这套二进制**没有跟过来**——文档与现实的偏移，正是该档开头自己写的
「文档里的'已知可用'会随环境漂移而失效」。

> ⚠️ 注意：`probe` 的**单个组件行**对 ffprobe 写「缺失…**仍可工作**」是**误导性文案**——
> ffmpeg 才是硬依赖，缺它整条链路停摆，而「仍可工作」四个字会让人以为无碍。

### 修法

```bash
sudo apt-get install -y ffmpeg     # 本机实测 sudo 免密可用；候选版本 7:8.0.1-3ubuntu2
```
并同步订正 `docs/本机环境事实.md` 为 **WSL 口径**。
（该项已于 2026-09-27 完成：该档原解释器路径全是 Windows 路径，现已按 WSL 重写；
复核 `grep -c 'C:\Users\lk' docs/本机环境事实.md` = 0。）

### 验收

1. `python3 skill/scripts/vt_pipeline.py probe` 退出码 **0**，且「主路线可用性: 可用」。
2. `ffmpeg -version` 与 `ffprobe -version` 均有输出（ffprobe **不得**再走 `ffmpeg -i` 回退）。
3. `python3 scripts/check-regression.py --e2e` 的 **R4 从 SKIP/FAIL 转为 PASS**（三态纪律：SKIP 不计通过）。

## 二、已实证的静默失效：画面 OCR 会悄悄返回空

### 现象

`vision_ocr()`（`skill/scripts/vt_pipeline.py:736-759`）只取 `message.content`：

```python
return ((j.get("message") or {}).get("content") or "").strip()   # 第 757 行
```

而请求体（第 738-744 行）**没有传 `think` 参数**，Ollama（实测 v0.34.3）对默认可能带思考的模型会走思考模式，把文字产在 `message.thinking`，`content` 于是为空。

### 实测（同一张帧 `output/BV1JMbp6MEo5/frames/f_001.jpg`，模型 `qwen3.5:9b`）

| 调用方式 | 耗时 | content | thinking | eval_count |
|---|---|---|---|---|
| 现状（无 `think` 参数） | **91.2s** | 116 字 | 1629 字 | 874 |
| `"think": false` | **25.9s** | 104 字 | **0 字** | 55 |
| 另一次现状调用 | 41.2s | **''（空）** | 有内容 | — |

**两个结论**：
1. **快 3.5x**——省掉的全部是思考 token（874 → 55）。
2. **识别内容无实质差异**：两者都识别出 11 行文字（`CodeCheers` / `bilibili` / `用户表达需求` / `通勤使用/预算≤800元/` / `重视降噪与舒适度` / `LLM` / `第一次交流(保存偏好)` / `PostgreSQL` / `用户提问` / `最近有什么耳机推荐` / `结合当前商品信息进行推荐`），差异仅 12 字，属空格/换行枝节。

### 为什么这条最该先修

它**正是本项目自己踩过并写进 `check_empty_ratio()` 文档字符串的坑**（第 780-784 行原话：「旧流程把有内容的帧记成空（视觉模型静默失败），导致成品里的画面断言在归档证据中"查无实据"，险些被误判为编造」）。

现有的空帧守卫（>1/3 告警）**只能事后告警，不能定位原因**；而且当空帧率恰好 ≤1/3 时**连告警都不触发**——失败仍然不可观测。这正中用户最在意的缺陷类型。

### 修法

1. `vision_ocr()` 请求体加 `"think": false`（一行）。
2. **兜底**：`content` 为空但 `thinking` 非空时，显式抛出/返回 `<<疑似思考模式吞输出>>`，不再静默返回 `""`。
3. 在 `帧OCR原始结果.md` 的元信息行记录实际耗时，便于回归比对。

### 验收

1. 同一帧连跑 3 次，`content` 均非空，且单帧耗时 **< 35s**（实测基准 25.9s）。
2. 人为把 `think` 改回缺省，机检**必须**报出异常（证明兜底真的拦住，而不是碰巧不触发）。
3. `frames` 输出的 `帧OCR原始结果.md` 内容与本次 11 行基线**语义一致**（人工比对，允许空格差异）。

## 三、结构性缺口：字幕优先「只在文档里」

`README.md` 与 `skill/SKILL.md` 都把 **字幕 > 转写** 列为第一优先级（"零误差，秒级"），决策树也画了「有字幕 ──▶ 直接用」这一支。

### 实际实现状况

```
$ grep -n 'subtitle|字幕|player/v2' skill/scripts/vt_pipeline.py
532:  "subtitle_available": 1 if ((view.get("subtitle") or {}).get("allow_submit")) else 0,
```

**只有这一行**——写了个字段，**没有任何取字幕的代码**。真正的字幕接口 `x/player/v2 → subtitle.subtitles[].subtitle_url` 在 `vt_pipeline.py` 里**一次都没出现过**。

唯一实现藏在 `skill/scripts/video_text_extract.py:471`（**可选适配器**，本机依赖缺失），而且那条路径的选择还是反的：

```python
if subs:
    print(f"  ℹ 发现 {len(subs)} 条字幕，但本链路优先音频转写（如需字幕请用 subs 子命令）")
```

→ **检测到字幕却仍走 ASR**，与文档声明的优先级矛盾。

### 收益（诚实标注）

- 有 CC 字幕的视频：**转写 58s → 拉字幕 ~0.3s**，且零识别误差。
- ⚠️ **本样例无法验证**：`BV1JMbp6MEo5` 实测 `x/player/v2` 返回 `subtitles: []`（**无字幕轨**），所以这条的收益需要**另找一个有 CC 字幕的 B站视频**做实测才能确证。
- ⚠️ 另需注意：B站的 **AI 字幕**通常要求登录 cookie，无 cookie 时可能拿不到。实现时必须把「无字幕」与「接口要登录」区分开输出（不能都当成「无字幕」静默降级）。

### 修法

在 `vt_pipeline.py` 加 `subtitle` 子命令（纯标准库：`x/player/v2` → `subtitle_url` → JSON 转 TXT/SRT），并让 `bili` 按「**有字幕走字幕 / 无字幕走 ASR**」分支；分支结果显式打印（走了哪条、为什么）。

### 验收

1. 对一个**有 CC 字幕**的视频实跑，产出字幕稿，且全流程 **< 5s**（对比同视频 ASR 路线的实耗）。
2. 对本样例（无字幕）实跑，输出**显式**写「无字幕轨，降级 ASR」，不得静默。
3. 字幕稿与 ASR 稿对同一视频做**人工抽 20 句比对**，字幕稿错字应显著更少（这是「字幕优先」成立的唯一判据）。

## 四、体验断层：一次产出要跑 4 条命令、无进度、无续跑

### 4.1 一条龙不含画面层

`bili --help` 实测只有 `--language` / `--segment`，**没有 `--frames`**。要拿到完整的「三层信息」成品，得手打：

```
vt_pipeline.py bili <URL>       # 元数据+音轨+转写
vt_pipeline.py frames <URL>     # 画面层（另起一次：重抓元数据、重下视频流）
```

而且 `frames` **会再下一份 4.0MB 视频流**（`video.m4s`），与 `bili` 下的 `audio.m4s` 是两次独立下载。

**修法**：`bili` 加 `--frames [--interval N]`，一条命令产出全套；`frames` 复用已下的 `video.m4s`（代码已有复用分支，第 812 行「复用已下载视频」，需确认「已下过就不重下」在一条龙里也成立）。

### 4.2 无进度、无 ETA、无续跑

当前 `transcribe` 每片打印一行「片 i/N ok（累计 X 字）」——**这点是好的**。但：
- `frames` 只在跑完才出结果，15 帧×25s 的 6 分钟里**没有任何进度百分比/ETA**；
- 没有 `--resume`：中断（**实测最大失败类因是宿主重启打断长任务**）后重跑要**从元数据开始全部重来**。

**修法**：① 每阶段打印 `[3/6] 转写中…（mm:ss / 预计 mm:ss）`；② 加 `--resume`：已有 `info.json` / `audio.wav` / `原始转写.txt` / **已完成帧的 OCR 结果**则跳过重做。

### 4.3 中间产物不清理

实测一次 314s 视频落盘 **26MB**，其中纯中间物占 23.3MB：

| 文件 | 体积 | 性质 |
|---|---|---|
| `segs/`（11 片） | 9.7MB | 纯中间物 |
| `audio.wav` | 9.6MB | 纯中间物 |
| `video.m4s` | 4.0MB | 画面层中间物 |
| `audio.m4s` | 2.5MB | 中间物 |
| **成品合计** | **≈2.7MB** | info/转写/OCR/弹幕 |

**修法**：默认清理中间物，`--keep-intermediate` 保留（排障需要）。⚠️ 但**不要擅自删已有产物**——`output/` 已在 `.gitignore`，属用户数据，清理只对新一次运行生效。

### 验收

1. `vt_pipeline.py bili <URL> --frames` **一条命令**产出与「4 命令手工跑」**同名的全套产物**（键数/文件数逐一比对）。
2. `--resume` 在删掉 `原始转写.txt` 后重跑，**不重新下载音频**（日志可证），总耗时显著低于全跑。
3. 新产物落盘体积 **< 5MB**（不含 `output/` 历史件），且 `--keep-intermediate` 能恢复 26MB 规模。

## 五、被实测**否决**的优化方向（记下来，省得白做）

优化不能只看「能不能做」，要看「做了有没有用」。以下两条**实测无收益**：

### 5.1 ASR 切片并发 —— ❌ 无效

| 方案 | 4 片合计 | 结论 |
|---|---|---|
| 串行 | 21.04s | 基线 |
| 并发（4 线程） | 23.94s | **0.88x，反而更慢** |

2 片并发复测：9.89s，而单片基准 5.1s ⇒ 宿主 ASR 服务**内部就是串行的**，并发只会增加排队与开销。
**外部推测**（未验证）：与 `emitter.compose` 相关的一次性 worker 创建有关。**不建议动 ASR 并发**。

### 5.2 视觉 OCR 并发 —— ⚠️ 收益很小

| 方案 | 2 帧合计 | 收益 |
|---|---|---|
| 串行 | 49.9s | 基线 |
| 并发 | 37.1s | **1.34x** |

有收益但远小于「修 `think`」的 3.5x。**优先级：先修 think，再谈并发**。

### 5.3 网络步骤并发 —— ❌ 无必要

实测 `view` 0.13s / `tag` 0.12s / `reply` 0.15s / `danmaku` 0.12s / `playurl` 0.15s，**合计仅 0.67s**。即便做成并发也就省 0.5s —— **不值得增加复杂度**。

> 这三条合计排除了「加并发」这个最直觉的方案。**真正的收益在 `think` 与「少跑几条命令」上。**

### A3-1 · R4 回归产物落进仓库根目录（已修）

## A5. 对本文档 §三 与 A3-2 的**自我订正**（2026-09-27 实测推翻）

### A5-1 · §三「字幕优先只在文档里」——判断方向对，但**成因与可行性都错了**

**我原先写的**：字幕优先只在文档、主路线零实现 ⇒ 加上就能「60s → ~1s」。

**实测推翻**：加了实现（`try_subtitle_route` 等）之后实测发现，
**无 cookie 时这条路线根本取不到字幕**：

| 实测 | 结果 |
|---|---|
| 探测热门/排行 **60 个视频** | 有可无 cookie 获取字幕轨的：**0 / 60** |
| `player/v2` 返回 | `subtitle.subtitles: []` 且 `need_login_subtitle: true` |
| 老样例 `BV1JMbp6MEo5` | `need_login_subtitle: true`（成品《整理说明》也早已写「CC 字幕需登录 cookie，未登录为空」） |

⇒ **§三 说的「60s → ~1s」收益，在无 cookie 场景下不成立**。正确的表述是：
**字幕优先是「有 cookie 才可用」的路线，不是「补上实现就能提速」的路线。**

**另一个更实的缺陷（原先没发现）**：旧代码用 `view.subtitle.allow_submit` 算 `subtitle_available`——
而 `allow_submit` 表示「**观众可否投稿字幕**」，与「本视频有没有字幕」无关。
实测 4 个不同视频该字段**恒为 false** ⇒ `subtitle_available` **实际永远是 0，是个死字段**。

**已修**（提交 `61813a4`）：
- 新增 `fetch_player` / `fetch_subtitles` / `subtitle_to_text` / `try_subtitle_route`；
  `info.json` 改记 **四态** `subtitle_state` = `has_subtitles` / `need_login_unknown` /
  `no_subtitle` / `probe_failed`，并记录 `subtitle_tracks`。
- 新增 `--subtitle-first` 与 `VT_BILI_COOKIE`（cookie 只从环境变量读，**不落盘、不进产物**）。
